# Merik support agent: trace audit (Week 04)

A small support agent (three tools, one loop) that runs the 20 scripted scenarios from
`merik-support-scenarios.md`, writes a trace for every step, and has one failure mode fixed:
repeated identical tool calls.

```
agent.py             the loop, the system prompt, the tracer, the DEDUPE_REPEATED_CALLS switch
fixtures.py          the 8 orders, 6 policies, get_order and check_policy (copied from the pack)
llm.py               Gemini and Anthropic adapters, plus a scripted model for offline tests
scenarios.json       the 20 scenarios and what each should do
checks.py            automatic path/reply flags (a first pass only)
run_scenarios.py     runs all 20 and writes traces/
summarize_traces.py  readable per-scenario view of a trace, and before/after diff
test_repeat_call.py  deterministic test for the repeated-call failure (no API key needed)
TRACE_REVIEW.md      the audit write-up (you fill this in from your own traces)
traces/              trace_before.jsonl, trace_after.jsonl (+ replies and summaries)
```

## Setup (Antigravity or any terminal)

1. Open this folder: File → Open Folder. Open the terminal (`` Ctrl+` ``).
2. Create an environment and install one provider SDK:
   ```bash
   python -m venv .venv
   # macOS/Linux:  source .venv/bin/activate
   # Windows:      .venv\Scripts\activate
   pip install google-genai      # or: pip install anthropic
   ```
3. Copy `.env.example` to `.env`, set `PROVIDER` and the matching key
   (`GEMINI_API_KEY` or `ANTHROPIC_API_KEY`). Optionally set `PRICE_IN_PER_M` and
   `PRICE_OUT_PER_M` so the `cost` field in the trace is not 0.
4. Check the install without a key: `python -m unittest -v test_repeat_call`
   (with the shipped baseline, one test fails on purpose; see step 2 below).

## The audit workflow (do these in order)

**1. Baseline run (fix OFF).** `DEDUPE_REPEATED_CALLS` in `agent.py` is `False` as shipped.
```bash
python run_scenarios.py --label before
```
This writes `traces/trace_before.jsonl`. Real model output varies, so do not edit this file by
hand and do not regenerate it after you have written your verdicts.

**2. Show the failure.** `python -m unittest test_repeat_call` fails with
`get_order issued 3 times, expected 1`. That is the red test.

**3. Commit the baseline.**
```bash
git init && git branch -M main
git add . && git commit -m "Baseline agent, scenarios, before traces, failing repro test"
```

**4. Read the traces, then the replies.**
```bash
python summarize_traces.py before
```
Read each scenario's steps against section 4 of the pack. `FLAG` lines are hints from
`checks.py`; they are heuristics, so read the steps yourself. Then fill in `TRACE_REVIEW.md`:
a verdict per scenario citing step numbers, at least one "right reply, wrong path" run, and at
least two failure modes the loop does not handle (each pointing at the trace that shows it).
Only name failure modes your own traces show.

**5. Apply the fix.** In `agent.py` set `DEDUPE_REPEATED_CALLS = True`, then:
```bash
python -m unittest -v test_repeat_call        # green
python run_scenarios.py --label after
python summarize_traces.py before after       # shows what changed
```
Fill in sections 4 and 5 of `TRACE_REVIEW.md` (the fix and the before/after numbers).

**6. Commit and push.**
```bash
git add . && git commit -m "Fix repeated identical tool calls; after traces; TRACE_REVIEW"
```

## Notes on how the agent works

- The loop talks to the model in plain JSON actions, so it behaves the same on any provider.
- The system prompt deliberately says nothing about repeated calls. That protection lives in
  the loop (`DEDUPE_REPEATED_CALLS`), not in a prompt instruction.
- A suppressed repeat is logged as tool `loop_guard` (not `get_order`), so the trace shows
  exactly one real `get_order` for scenario 18.
- If a run hits `MAX_STEPS` with no `draft_reply`, the trace ends with a `run_aborted` step.
- Each trace line: `scenario, sender, step, tool, args, result, ms, cost` plus token counts.
  `ms` covers the model call and the tool call for that step.
